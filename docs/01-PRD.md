## FP-01：MySQL 多版本管理（Docker 容器方案）

> 📌 **ADR-08 修正**：调研后，多版本方案从"tarball 物理安装"升级为 **Docker 容器隔离**。
> 借鉴 restore-drill 的思路：每次恢复启动对应版本的 MySQL Docker 容器，天然解决多版本共存。

**触发方式**：恢复流程内部自动调用 / 手动 CLI（`toolkit mysql ensure --version 8.0.35`）

**输入**：
- 版本号（如 `8.0.35`、`5.7.44`）
- 容器名前缀（默认 `drill-mysql-{version}`）
- datadir 挂载路径（恢复时挂载，供 xtrabackup copy-back）

**处理逻辑**：
1. 检查恢复机 Docker 是否可用（前置检查）
2. 检查本地是否已有该版本镜像（`docker images mysql:{version}`）
3. 不存在则 `docker pull mysql:{version}`（从官方仓库，含重试）
4. 启动容器：`docker run -d --name {container} -v {datadir}:/var/lib/mysql mysql:{version}`
5. 工具能通过 `docker start/stop/exec` 控制该容器
6. 记录到元数据库（容器ID、版本、状态）

**输出**：
- 可用的 MySQL Docker 容器（对应版本）
- 可被启停/执行命令的控制能力（经 `docker exec`）

**异常处理**：
- Docker 未安装/未启动：明确报错，提示前置安装（恢复机必须预装 Docker）
- `docker pull` 失败：重试 3 次（网络问题），仍失败告警并跳过
- 端口冲突：自动分配空闲端口或报错
- 版本不受支持：明确报错（支持的版本白名单）

**不做**：
- 不用 yum/apt 安装 MySQL（避免污染系统）
- 不物理解压 tarball 到 `/opt/mysql-versions/`（已废弃此方案，改用 Docker）
- 不做 MySQL 集群/复制（单容器即可满足恢复演练）

## FP-02：Xtrabackup 备份触发、登记与拉取（ADR-06 接管模式 + ADR-08 架构标杆）

**触发方式**：定时（替代原 crontab）/ 手动 CLI / 恢复流程内部按需拉取

> ⚠️ 范围说明：用户选定接管现有 crontab 备份（ADR-06）。采用分阶段交付——
> **Sprint 1-2 先只做"拉取 + 登记 + 定位"**（用现有 crontab 备份跑通演练），
> **Sprint 3 再做"触发备份"**（真正替换 crontab）。

> 📌 **ADR-08 架构标杆**：备份模块（Sprint 3 实现"触发备份"时）以
> **pyxtrabackup**（`deviantony/xtrabackup-scripts`）的分层架构为标杆：
> - 命令执行收口到 `command_executor`（列表参数，防注入）
> - 增量备份用 LSN 追踪（读 `xtrabackup_checkpoints` 的 `to_lsn`）
> - 备份流水线：前置检查 → backup → prepare → 压缩打包 → 归档 → 清理 → webhook
> - 全部用 `xtrabackup` 命令（非已废弃的 innobackupex），兼容 MySQL 8.0
> - 远程 NAS 推送参考 pyxtra 的 `rsync -avrP` 用法
> 详见 `docs/07-技术调研报告.md`

**输入**：
- 源实例信息（IP、port、版本、只读 + 备份账号）
- 备份源机地址（备份归档所在机器）
- 备份方式（全量/增量，本期全量）

**处理逻辑**：
1. **登记**：SSH 到备份源机，扫描备份目录，登记可用备份到 `backups` 表
2. **定位**：恢复时按"源实例 → 最新可用全量备份"定位
3. **拉取**（ADR-04 scp 模式）：恢复前通过 SSH+scp 把备份从源机拉到恢复机临时目录
4. **触发**（Sprint 3）：SSH 到源生产机执行 `xtrabackup --backup`，产出归档到备份源机

**输出**：
- 给定源实例，返回最新可用备份路径
- 拉取完成后，返回恢复机上的本地备份路径

**异常处理**：
- 备份源机 SSH 不通：记录不可用，跳过该实例
- 备份文件不完整（缺 `xtrabackup_info`）：标记损坏，不用于恢复
- scp 拉取失败：重试，仍失败则该实例跳过并告警
- 磁盘不足（恢复机临时目录）：预检查，不足告警停止

**不做**：
- 不做增量备份（本期全量，增量留 P2）
- Sprint 1-2 不实现"触发备份"，仅拉取 + 登记

## FP-03：自动化恢复演练编排（🔥 核心）

**触发方式**：手动 CLI（`toolkit drill run`）/ Web 点击 / 定时

**输入**：
- 恢复目标主机（一台空服务器，工具可管理它）
- 要演练的源实例集合（全部 / 指定列表）
- 执行模式：立即 / 定时（cron 表达式）
- 验证规则（查哪个库、哪张表、期望结果）

**处理逻辑**：
1. 收集所有待演练备份，按 **MySQL 版本升序、IP 升序** 排队（同版本连续恢复，减少重装）
2. 对队首任务：
   - 若当前目标机 MySQL 版本 ≠ 备份版本 → 调用 FP-01 安装对应版本
   - 确认工具能 start/stop 该 MySQL 实例
3. 执行恢复：`xtrabackup --prepare` → `--copy-back` → `chown datadir` → 启动实例 → 登录验证（FP-04）
4. 验证通过 → 归档日志（FP-08）→ 清理 datadir → 取下一个任务
5. 同版本继续恢复（跳过重装）；不同版本先重装再恢复
6. 全部完成 → 生成报告（FP-06）+ 通知（FP-07）

**输出**：
- 每个实例的恢复结果（成功/失败/重试中）
- 最终 Markdown 报告 + 企业微信通知

**异常处理**：
- 单实例恢复失败 → 进入重试队列，重试 1 次（FP-05）
- 重试仍失败 → 记录失败原因，继续下一个，不阻塞整体
- 目标机磁盘不足 → 预检查，不足则告警停止

**不做**：
- 不做增量恢复（本期）
- 不并发在同一台目标机恢复多个实例（串行，避免 datadir 冲突）—— 多目标机并发是 P2

## FP-04：恢复后验证

**触发方式**：恢复流程内部，实例启动后

**输入**：
- 已启动的 MySQL 实例连接信息
- 验证规则（来自配置）：
  - 检查 xtrabackup 日志关键字（`completed OK!`）
  - 查询指定库 `SELECT COUNT(*) FROM db.table`
  - 可选：期望行数 > N

**处理逻辑**：
1. grep xtrabackup 日志确认 `completed OK!`
2. 连接 MySQL 执行验证 SQL
3. 比对期望结果

**输出**：`PASS` / `FAIL` + 证据（日志片段、查询结果）

**异常处理**：
- 连不上 MySQL：标记 FAIL，附启动日志
- 查询超时：FAIL

**不做**：
- 不做业务级数据正确性校验（只验证"能起来 + 表能查"）

## FP-05：任务队列与重试

**触发方式**：恢复流程内部

**输入**：恢复任务列表

**处理逻辑**：
1. 任务入队，状态机：`PENDING → RUNNING → SUCCESS / FAILED → RETRYING → SUCCESS / FAILED_FINAL`
2. 失败任务最多重试 1 次
3. 支持断点续跑（崩溃后重启从上次未完成的继续）

**输出**：任务状态流转记录

**异常处理**：
- 工具自身崩溃：重启后从元数据库恢复任务状态

**不做**：
- 不做分布式任务队列（单机内存队列 + 持久化到 SQLite 足够）

## FP-06：Markdown 报告生成

**触发方式**：演练结束后

**输入**：本次演练所有任务结果

**处理逻辑**：用 Jinja2 模板渲染

**输出**：Markdown 报告，包含：
- 汇总：总数 / 成功 / 失败 / 重试
- 明细表：实例、版本、备份时间、恢复耗时、结果、失败原因
- 验证日志摘要

**不做**：不做 PDF（P2）

---

## FP-07：企业微信通知

**触发方式**：报告生成后

**输入**：报告摘要 + webhook URL

**处理逻辑**：POST 到企业微信群机器人 webhook

**输出**：发送成功/失败

**异常处理**：webhook 失败重试 3 次，仍失败记录日志（不阻塞主流程）

**不做**：不做邮件/钉钉（P2，但 notifiers 设计成可扩展）

---

## FP-08：审计日志归档

**触发方式**：每个成功恢复后

**输入**：xtrabackup 日志、验证日志、实例信息

**处理逻辑**：按 `/归档目录/YYYY-MM-DD/{源IP}_{版本}/` 结构保存

**输出**：可被领导审计的日志文件集合

**不做**：不做日志全文检索（P2）

## FP-09：Web 触发入口（最小）

**触发方式**：浏览器访问

**输入**：点"开始演练"按钮

**处理逻辑**：调起 FP-03，展示进度

**输出**：进度页面 + 报告下载

**不做**：不做复杂 RBAC、不做历史趋势图（P2）

## 非功能需求（NFR）

| 类别 | 要求 |
|---|---|
| 可观测 | 工具自身有日志，任务状态可查 |
| 可恢复 | 元数据持久化，崩溃可续跑 |
| 可扩展 | inspector/notifier 用插件式接口，后续加功能不改核心 |
| 安全 | 见 `04-安全设计.md` |
| 性能 | 单目标机串行恢复，支持多目标机并发（P2） |
