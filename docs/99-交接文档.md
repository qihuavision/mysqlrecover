### ADR-08 详述：技术选型与参考来源（2026-08-13 锁定）

> 完整调研过程见 [`docs/07-技术调研报告.md`](07-技术调研报告.md)

**背景**：立项后进行了两轮 GitHub 开源项目调研，评估可复用的实现，避免重复造轮子。

**决策**：

| 子决策 | 选定 | 备选（未采用） | 理由 |
|---|---|---|---|
| 备份模块架构标杆 | **pyxtrabackup**（`deviantony/xtrabackup-scripts`）分层架构 | pyxtra（工程不合格）、gox（语言不符） | 工程规范最高：列表参数防注入、异常体系、logging、LSN 增量追踪、10步流水线 |
| 备份命令 | **`xtrabackup`**（8.0 兼容） | innobackupex（pyxtrabackup 原用，已废弃） | innobackupex 在 XtraBackup 8.0 已移除 |
| 增量备份追踪 | **LSN**（读 `xtrabackup_checkpoints` 的 `to_lsn`） | 目录名追踪（pyxtra 方式，脆弱） | LSN 是官方推荐方式，可靠 |
| 多版本恢复方案 | **Docker 容器隔离** | dbdeployer 物理多实例、tarball 多实例 | Docker 更干净（每次全新环境）、易清理；借鉴 restore-drill |
| 恢复演练设计 | 声明式配置 + 验证 SQL + 审计报告 | mneme（Ansible，重） | 借鉴 restore-drill（`RamazanKara/restore-drill`） |
| 远程 NAS 备份 | **rsync 推送** | NFS 挂载（依赖运维） | 参考 pyxtra 的 rsync 用法，工具自管 |
| 压缩 | tar.gz（备份模块内置） | — | 参考 pyxtrabackup |
| 保留策略 | 按天数/份数自动清理 | — | 新增（参考项目都没有，自研） |

**⚠️ 重要修正（覆盖 ADR-02 部分）**：
原 ADR-02 定为"官方 tarball 装 MySQL"，调研后**多版本方案升级为 Docker 容器隔离**：
- 恢复时不再在恢复机物理安装多版本 MySQL，而是为每次恢复启动对应版本的 Docker 容器（如 `mysql:8.0.35`、`mysql:5.7.44`）
- 这**不影响 FP-01 的 tarball 安装逻辑**（Docker 镜像本身就是版本隔离），但实现方式从"解压 tarball 到 `/opt/mysql-versions/`"变为"拉取/启动对应版本 Docker 镜像"
- **前置依赖**：恢复机必须安装 Docker。FP-01 的职责从"装 MySQL"调整为"管理 MySQL Docker 容器（拉镜像、启停、挂载 datadir）"

**不直接 fork 这些项目的原因**：
1. pyxtrabackup 依赖过老（Python 3.4 / innobackupex / docopt），改造量 ≈ 重写量
2. restore-drill 是 Go 写的，与本项目 Python 栈不符
3. 本项目要对上百实例负责，自研代码可完全掌控

**借鉴方式**：参考设计思路和架构，不复用代码。涉及 Apache 2.0 项目（pyxtrabackup、restore-drill），若复用代码片段须在 NOTICE 声明。

### ADR-09 详述：Docker 恢复架构实现细节（2026-08-13 锁定）

> ADR-08 确定了"用 Docker 容器隔离多版本 MySQL"。ADR-09 锁定具体怎么用 Docker。

**核心原则**：宿主机跑 xtrabackup + datadir 挂载进容器 + host 网络 + 固定单端口 + 容器常驻。

**子决策**：

| 子决策 | 选定 | 理由 |
|---|---|---|
| xtrabackup 执行位置 | **宿主机**（非容器内） | 不用自建含 xtrabackup 的镜像，用官方 `mysql:8.0` 镜像即可，最简单 |
| datadir 位置 | **宿主机** `/data/drill/{version}/datadir/`，挂载进容器 | 宿主机可跑 copy-back；独立目录避免与宿主 MySQL 权限冲突 |
| 网络模式 | **host**（`--network host`） | 直接用宿主机端口，最简单 |
| 端口策略 | **固定单端口 13306**（串行复用） | ADR-05 串行恢复，同一时刻只有一个容器跑，端口不冲突 |
| 容器生命周期 | **常驻**（按版本复用，不随实例删除） | 上百实例恢复时省去反复 docker run/pull 开销；同版本连续恢复直接复用 |
| 容器内 MySQL uid | **999:999**（官方镜像 mysql 用户） | copy-back 后宿主机 datadir 必须 `chown 999:999`，代码自动处理 |

**常驻容器池设计**：
- 每个需要的 MySQL 版本对应一个常驻容器：`drill-mysql-{version}`（如 `drill-mysql-8035`）
- 所有常驻容器配置 `--port=13306`（串行不冲突）
- 容器启动时 datadir 挂载到 `/data/drill/{version}/datadir`
- 首次需要某版本时 `docker run -d` 创建并加入池；之后 `docker start/stop` 复用

**单实例恢复标准流程**（串行）：
```
1. 确认目标版本常驻容器存在（首次则 docker run 创建，已存在则复用）
2. docker stop {当前容器}          # 若有其他版本容器在跑，先停掉
3. docker start {目标版本容器}      # 启动目标版本容器（端口 13306）
4. docker stop {目标版本容器}       # 立即停（copy-back 需要 MySQL 不运行）
5. 清空 /data/drill/{version}/datadir/*
6. 宿主机：xtrabackup --prepare --target-dir={备份临时目录}
7. 宿主机：xtrabackup --copy-back --target-dir={备份临时目录} --datadir=/data/drill/{version}/datadir
8. 宿主机：chown -R 999:999 /data/drill/{version}/datadir
9. docker start {目标版本容器}      # 启动，加载恢复后的 datadir
10. 连 127.0.0.1:13306 执行验证 SQL（FP-04）
11. 验证通过 → 归档日志（FP-08）
12. 取下一个任务：同版本 → 回到步骤4；不同版本 → 回到步骤2
```

**前置依赖（恢复机 bootstrap 时安装）**：
1. Docker（必装）
2. xtrabackup（必装，宿主机跑备份恢复）
3. 创建 `/data/drill/` 目录

**⚠️ 关键实现约束**：
- 所有 docker 命令经 `core/executor.py` 执行（SSH 到恢复机跑）
- 串行保证（ADR-05）：工具必须确保同一时刻只有一个常驻容器在 running 状态
- copy-back 前必须 `docker stop`，否则 datadir 被锁导致恢复失败

### ADR-10 详述：实现细节锁定（2026-08-13）

> 锁定验证规则、密码安全、配置格式、错误日志采集等实现细节。

**子决策**：

#### 1. 实例清单格式：单文件 YAML
- 所有实例写在 `config/instances.yaml`，DBA 批量编辑
- 结构：`defaults`（全局默认）+ `instances`（实例列表，每实例可覆盖默认）

#### 2. 密码安全：环境变量方案
- 密码**绝不写进配置文件**，存管理机环境变量 `DRILL_MYSQL_PWD`
- 工具启动时从环境变量读取，运行时注入给 xtrabackup（经 `--defaults-file` 临时文件或 stdin，不进 ps/history）
- 符合 `04-安全设计.md` 要求；后续可无缝升级到 Vault（运行时注入环境变量）
- **前提**：上百实例统一用一个只读备份账号（DBA 惯例）

#### 3. 恢复验证规则：自动发现（核心创新）
不用为每个实例手写验证 SQL，工具自动发现业务库表验证：

```
自动验证流程：
1. 连接恢复出的实例 127.0.0.1:13306
2. 查所有库 → 过滤系统库（mysql, information_schema, performance_schema, sys, test）
3. 对剩余业务库，选 TABLES 数量最多的库作为验证库
4. 在验证库中，选 TABLE_ROWS > 0 的第一张表
5. SELECT COUNT(*) FROM {库}.{表} → 结果 > 0 则 PASS
```

**边界判定**：
| 情况 | 判定 |
|---|---|
| 过滤系统库后无业务库 | **PASS**（MySQL 能起来即说明 datadir 恢复成功，只是无业务数据） |
| COUNT(*) > 0 | PASS |
| COUNT(*) = 0 或查询失败 | FAIL |

#### 4. 验证失败/启动失败处理
- **验证 FAIL**：自动进重试队列（FP-05），重试 1 次仍失败则记录失败 + 附详细诊断（发现了哪些库、选了哪个库哪张表、COUNT 结果、报错）
- **容器启动失败**（docker start 失败）：**必须采集并保留日志**
  - `docker logs {容器}` 抓取容器错误输出
  - 检查挂载 datadir 下的 `{hostname}.err`（MySQL error log）
  - 两份日志归档到 `/归档目录/YYYY-MM-DD/{源IP}_{版本}/error/`
  - 标记该实例失败，附日志路径

#### 5. 配置文件 YAML 结构（草案）
```yaml
# config/instances.yaml
defaults:
  backup_user: backup_reader          # 统一只读备份账号
  # password 不写这里，来自环境变量 DRILL_MYSQL_PWD
  drill_port: 13306                   # 固定端口（ADR-09）
  docker_datadir_base: /data/drill    # 容器 datadir 挂载根
  verify:
    exclude_system_dbs: [mysql, information_schema, performance_schema, sys, test]

instances:
  - name: order-db-prod-01
    host: 10.0.1.10                   # 源实例 IP
    port: 3306
    mysql_version: "8.0.35"
    backup_source:                    # 备份在哪台机器
      host: 10.0.1.250
      path: /backups/order-db-prod-01/
    # 可选：覆盖默认验证规则（绝大多数实例用自动发现即可，无需配）
```

## 7. 已知问题 / 坑
- xtrabackup 版本需与 MySQL 版本匹配，需维护版本矩阵（config 已配）
- MySQL 8.0 默认 `caching_sha2_password`，连接器需注意（PyMySQL 已支持）
- SSH 免密需提前打通：管理机→恢复机、管理机→备份源机
- 恢复机磁盘：每次恢复前清 datadir + 拉取备份，注意临时空间
- 上百实例全量演练耗时长，需断点续跑（Sprint 2）
- 🆕 **Docker 容器内 mysql 用户 uid=999**：copy-back 后宿主机 datadir 必须 `chown 999:999`（代码自动处理）
- 🆕 **copy-back 前必须 docker stop**：否则 datadir 被锁导致恢复失败
- 🆕 **串行保证**：同一时刻只能有一个常驻容器在 running（都用 13306 端口）
- 🆕 **恢复机前置依赖**：必须预装 Docker + xtrabackup + 创建 `/data/drill/`
