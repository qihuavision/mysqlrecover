# AI 协作开发指南

> 本文档是「MySQL 自动化备份与恢复演练工具」的 AI 协作开发方法论。
> 它回答的不是"项目做什么"（那是 [立项书](00-立项书.md) 和 [PRD](01-PRD.md) 的事），而是**"怎么用 AI 把它做出来，且不失控"**。
> 任何新会话接手前，建议先读本文件 + [交接文档](99-交接文档.md)。

---

## 0. 开工前的三个"灵魂问题"

让 AI 写一行代码之前，必须能用一句话回答这三个问题。答不上来就不要立项：

| 问题 | 回答模板 | 本项目的回答 |
|---|---|---|
| **给谁用？** | 角色 + 使用场景 | DBA，日常备份 + 定期恢复演练 |
| **解决什么痛点？** | 现在怎么做、有多痛 | 上百个实例手动逐台恢复，单次演练耗费大量人力 |
| **不做什么？（最重要）** | 明确排除项 | 不做监控告警（有 Prometheus）、不做 HA（有 Orchestrator）、不做数据同步（有 Canal） |

> ⚠️ 第三个问题最关键。AI 协作项目失败 **80% 是因为"范围蔓延"** —— AI 不知道边界，就会越写越大，最后失控。明确"不做什么"比"做什么"更重要。
> 本项目的"不做"清单已锁定在 [立项书 §3](00-立项书.md#3-范围)。

## 1. 立项文档：让 AI 准确理解项目

不要直接对 AI 说"帮我写个 MySQL 运维工具"。要先用一份**立项书（Charter）**把项目定义死。

✅ 本项目已完成：[`docs/00-立项书.md`](00-立项书.md)。该文件是整个项目的"宪法"，每次开新会话都先让 AI 读它。

立项书必须包含：背景痛点、SMART 目标、范围（做 / 不做）、用户角色、技术约束、成功标准。

---

## 2. 需求文档（PRD）：把"做什么"拆到 AI 能执行

立项书是"为什么"，PRD 是"做什么"。PRD 要拆到**功能点级别**，每个功能点要有输入 / 输出 / 异常 / 不做。

✅ 本项目已完成：[`docs/01-PRD.md`](01-PRD.md)。

### 功能点卡片模板

```markdown
## 功能点：XXX

**触发方式**：定时任务 / 手动 CLI / 页面点击
**输入**：
- 字段 1（来源）
- 字段 2（默认值）

**处理逻辑**：
1. 步骤 1
2. 步骤 2

**输出**：
- 产物格式
- 通知渠道

**异常处理**：
- 异常 A：处理方式
- 异常 B：处理方式

**不做**：
- 不做 X
- 不做 Y
```

> 💡 **关键技巧**：每个功能点都要写"不做"。这是给 AI 画的护栏。

### 本项目功能优先级矩阵

参考下表排开发顺序，**先做安全的只读功能，架构稳了再碰危险操作**：

| 优先级 | 模块 | 难度 | 危险等级 |
|---|---|---|---|
| P0 | 多版本 MySQL 自动安装 | ⭐⭐ | 🟡 中（在隔离恢复机） |
| P0 | 自动恢复演练编排 | ⭐⭐⭐⭐ | 🟡 中（隔离环境） |
| P0 | 恢复后验证 + 审计日志 | ⭐⭐ | 🟢 安全（只读查询） |
| P1 | Markdown 报告 + 企业微信通知 | ⭐⭐ | 🟢 安全 |
| P2 | 备份接管（接管现有 crontab） | ⭐⭐⭐ | 🔴 危险（碰生产备份任务） |

> 📌 本项目立项"做"里含自动备份，但**分阶段实施**：Sprint 1-2 先做恢复演练（最大痛点），Sprint 3 再做备份接管。

## 3. 架构设计：写代码前定死

让 AI 写代码前，先产出设计文档，审核通过后再写代码。**否则 AI 每次会话都会重新设计架构，导致代码风格不一致。**

✅ 本项目已完成：
- [`docs/02-架构设计.md`](02-架构设计.md) —— 模块职责、调用关系、依赖图
- [`docs/03-数据库设计.md`](03-数据库设计.md) —— 工具自己的元数据库（配置 / 历史记录）
- [`docs/04-安全设计.md`](04-安全设计.md) —— DBA 工具专属安全设计

### 本项目锁定的架构一句话

> **管理机**（工具 + SQLite）─SSH─▶ **恢复机**（装 MySQL + 恢复 + 验证）；管理机 ─SSH/scp─▶ **备份源机**（拉备份）。所有远程操作统一走 `src/toolkit/core/executor.py`。

### 推荐目录结构

```
mysql-recovery-toolkit/
├── docs/                    # 所有文档（立项书、PRD、设计、交接）
├── src/toolkit/
│   ├── core/                # 核心抽象（连接、实例、执行器、安全）
│   │   ├── executor.py      # SSH 执行抽象层（LocalExecutor + SSHExecutor）
│   │   └── safety.py        # dry-run、白名单
│   ├── installers/          # MySQL 多版本安装
│   ├── backup/              # 备份登记、定位、执行
│   ├── recovery/            # 恢复演练编排（prepare/copy-back/验证）
│   ├── reporters/           # 报告生成
│   ├── notifiers/           # 企业微信通知
│   └── cli.py               # 命令行入口
├── tests/                   # 测试（每个模块对应一个测试）
├── config/                  # 配置模板
└── scripts/                 # 部署脚本
```

## 4. AI 协作开发工作流：怎么"开写"

这是核心。AI 开发和传统开发的根本区别：**AI 的上下文是有限的，必须分批、可验证地推进。**

### 4.1 黄金法则

1. **一次一个功能点**：不要一次让 AI 写整个模块。每次只写一个 installer / recovery 步骤。
2. **测试先行**：先让 AI 写测试用例（基于 PRD 的输入/输出），再写实现。
3. **可运行里程碑**：每完成一个功能点，必须能跑通一条命令。
4. **小步提交**：每个功能点完成后 `git commit` 一次（改坏了能回滚）。

### 4.2 单次会话的标准开场白

每次开新会话，用这个模板（不要寒暄，直接给上下文）：

```markdown
你是一位资深 Python 工程师，帮我开发 MySQL 自动备份与恢复演练工具。

请先阅读以下文档了解项目背景：
1. docs/00-立项书.md（项目目标和范围）
2. docs/01-PRD.md（需求，重点看"功能点：XXX"这一节）
3. docs/02-架构设计.md（已有的模块划分）
4. docs/99-交接文档.md（当前进度）

本次任务：实现【功能点：XXX】

要求：
1. 先看 tests/ 下对应测试是否存在，不存在则按 PRD 写测试
2. 实现对应模块
3. 在 cli.py 注册命令
4. 跑通测试后告诉我结果
5. 完成后更新 docs/99-交接文档.md

约束：遵守 docs/02-架构设计.md 的目录结构和命名规范。
```

### 4.3 分阶段交付计划

本项目采用 4 个 Sprint，每个 Sprint 结束必须更新 [交接文档](99-交接文档.md)：

| Sprint | 目标 | 产出 | 验收 |
|---|---|---|---|
| Sprint 1 | 骨架 + 单实例恢复跑通 | executor.py + MySQL 安装 + 一个备份恢复 + 验证 | `drill run` 命令跑通 |
| Sprint 2 | 恢复编排（多实例、版本排队、重试） | 编排引擎 | 一次跑通 N 个实例 |
| Sprint 3 | 报告 + 企业微信通知 + 日志归档 | 报告/通知/归档 | 出报告、发通知、可审计 |
| Sprint 4 | 稳定性、文档、Docker 化交付 | 完整交付包 | 可交付给其他 DBA |

## 5. 交接文档：迁移给另一个 AI 的关键

这是 AI 协作开发**最重要的一份文档**。它让任何新的 AI 会话能在 5 分钟内接手项目。

✅ 本项目已完成：[`docs/99-交接文档.md`](99-交接文档.md)。

### 交接文档必须包含

1. 项目一句话
2. 当前状态（进度 / 最后可运行版本 / 健康度）
3. 已完成功能表（功能 / 文件 / 状态 / 测试）
4. 进行中 / 下一步
5. 关键技术决策（ADR）
6. 已知问题 / 坑
7. 本地运行方式
8. **不要做的事**（给下一个 AI 的警告）
9. 待办池（未来想法，现在不做）
10. 上次会话遗留问题

> 🎯 **交接文档的检验标准**：把它发给一个完全没参与过项目的 AI，让它复述"这个项目现在在做什么、下一步做什么、有什么坑"，如果它能答对，文档就合格了。

### 增量更新原则

不要等写到一半才生成交接文档，而是**每次会话结束都增量更新**。如果已经写了一半才发现没文档，用这个 prompt 补救：

```markdown
请扫描当前项目代码，帮我生成/更新以下文档：
1. 架构现状文档（基于实际代码画模块依赖图，从代码反推职责，不要猜）
2. 交接文档（扫描所有 Python 文件统计完成度、运行测试、从注释和 TODO 提取已知问题）
3. README.md（安装步骤 + 基于 CLI 的使用示例）
要求：基于代码事实，不要编造。不确定的地方标注 [待确认]。
```

## 6. DBA 工具专属：最容易忽略的坑

对 DBA 工具，下面这些比功能本身更重要。详见 [`docs/04-安全设计.md`](04-安全设计.md)，这里是要点速查。

### 6.1 安全设计（⚠️ 不过关不能上线）

| 安全项 | 做法 |
|---|---|
| 凭据存储 | MySQL 密码**绝不能**明文存配置文件，用环境变量 / Vault / 加密配置 |
| 最小权限 | 工具连接 MySQL 的账号只要 `PROCESS, REPLICATION CLIENT, SELECT`，**绝不要 root** |
| Dry-run 模式 | 任何有副作用的操作，默认 `--dry-run`，先打印不执行 |
| 操作白名单 | 维护"允许执行的 SQL 模式"白名单，不在白名单的一律拒绝 |
| 审计日志 | 工具执行的每一条 SQL 都落审计表（who / when / what / result） |
| 审批流 | 危险操作必须人工确认，不能全自动 |
| 网络隔离 | 工具部署位置要能访问生产库，但生产库不能反向访问工具 |

### 6.2 恢复演练专属问题（本项目已识别）

> 这些是通用方法论里没有、本项目特有的坑，开发时必须先决策：

1. **恢复后用什么密码登录验证？**
   xtrabackup copy-back 后，恢复出的 MySQL 是生产的字节级副本，账号密码都是生产那套。
   - 方案 A：用生产只读账号密码登录验证（简单，但验证依赖生产凭据）
   - 方案 B：用 `--skip-grant-tables` 启动做验证（与生产密码解耦，隔离性更好）
   - 🔖 决策记录在 [交接文档 ADR](99-交接文档.md)

2. **xtrabackup 在恢复机上谁来装？**
   恢复机是"DBA 提供的空服务器"，工具首次运行时需自动 bootstrap xtrabackup，或写成明确的人工前置步骤。

3. **备份源机是一台还是多台？**
   上百个实例的备份是集中在一台备份服务器，还是分散在各源机本地？决定 scp / locator 怎么写。

### 6.3 测试策略

DBA 工具测试比普通项目难，因为**不能在真生产库测**。详见 [`docs/05-测试策略.md`](05-测试策略.md)。

```
tests/
├── unit/              # 纯逻辑测试，mock 掉数据库
├── integration/       # 用 Docker 起一个 MySQL 测
├── fixtures/          # 测试用的 SQL 样本、xtrabackup 备份样本
└── golden/            # 金标准输出（回归测试，防止 AI 改坏）
```

> 重点：准备一份"金标准"测试数据（真实的备份样本、真实的验证输出），每次 AI 改代码后跑回归，防止 AI 优化时改坏已有功能。
