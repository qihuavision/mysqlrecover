# 项目立项书：MySQL 自动化备份与恢复演练工具

> 本文件是项目的"宪法"。任何新会话接手前必读。最后更新：2026-08-12

---

## 1. 背景与痛点

### 现状（3 个具体场景）
1. **日常备份**：通过自写 crontab 定时任务，对上百个 MySQL 实例（不同版本，5.7 / 8.0 混杂）用 xtrabackup 做物理备份。
2. **定期恢复演练（核心痛点）**：需要定期对所有备份做恢复验证。目前流程完全手动，每台机器都要重复：
   - 手动创建对应版本的 MySQL 实例
   - 用 xtrabackup 恢复到对应版本（prepare → copy-back）
   - 查看恢复日志、登录 MySQL 查询某张表验证成功
3. **版本碎片化**：上百个实例跨多个 MySQL 版本，每切换一个版本就要重装一次 MySQL，人工极易出错。

### 痛点（量化）
- 上百个实例逐台手动恢复，单次全量演练耗费大量人力物力
- 流程依赖人，易漏、易错、无法审计
- 恢复成功率没有结构化记录，无法证明"备份真的可用"

---

## 2. 目标（SMART）

**3 个月内**，完成工具的「自动化备份 + 自动化恢复演练」：

- DBA 只需**提供一台空的服务器**，工具自动：
  1. 在该服务器上安装所需版本的 MySQL
  2. 依次用所有备份执行恢复
  3. 恢复后自动验证，并把验证成功的日志归档到指定目录供审计
- 覆盖 **[ 自动安装 MySQL / 自动备份 / 自动恢复演练 ]** 3 个核心场景
- **可衡量**：一次全量演练的人力介入从"上百次手动操作"降到"1 条命令 + 审阅报告"

### 通用性目标（Sprint 7 增补）

**任何公司、任何 DBA，拿去就能一键使用**：

- 版本白名单默认为空（不限制）——遇到没见过的 MySQL 版本，自动拉对应 Docker 镜像建恢复环境，不用改代码不用改配置
- 备份版本自动从备份文件检测（配置填错自动纠正），不依赖人工维护版本清单
- redo 格式兼容自动判断（依据 Percona 官方变更记录），DBA 不需要懂 redo 分水岭也能安全恢复：
  恢复前自动完成三步核对——①备份是什么版本 ②当前恢复环境是什么版本 ③两者 redo 格式是否同代
  （MySQL 8.0 历史上改过两次 redo 格式：8.0.20 和 8.0.30，跨代不能直接恢复，工具自动隔离）
- xtrabackup 版本冲突（5.7 要 2.4、8.0 要 8.0）由工具内置容器方案解决，宿主机不用装多份

---

## 3. 范围

### 做（In Scope）
- 多版本 MySQL 自动安装管理（5.7 / 8.0 及后续）
- Xtrabackup 备份的登记、定位、执行
- 自动化恢复演练编排（含版本排队、重试、验证）
- 恢复后验证 + 审计日志归档
- Markdown 报告 + 企业微信通知
- 保留扩展能力（后续可加巡检、DDL 审核等，但本期不做）

### 不做（Out of Scope）— 护栏
- ❌ 监控告警（已有 Prometheus）
- ❌ 高可用切换（已有 Orchestrator）
- ❌ 数据同步（已有 Canal）
- ❌ 本期不做 Web UI 的复杂功能（CLI 优先，Web 仅做触发入口）
- ❌ 不碰生产库业务数据（只读源实例元信息，不在生产库写任何业务表）

## 4. 用户与角色
| 角色 | 权限 | 场景 |
|---|---|---|
| DBA（主用户） | 全功能 | 配置实例、触发演练、查看报告 |
| 研发（次用户） | 只读 | 查看演练报告（证明备份可用） |
| 领导（审计方） | 只读 | 审阅归档的验证日志 |

---

## 5. 技术约束
- 语言：**Python 3.11**
- 部署：**Docker 单机**（工具自身）
- 依赖的 MySQL 版本：**5.7 / 8.0**（恢复目标多版本，工具需兼容）
- 操作系统：Linux（待确认具体发行版，见交接文档待确认项）
- **绝不在生产库执行写操作**

---

## 6. 成功标准（验收）
- [ ] 给定一台空服务器，一条命令可完成全量恢复演练
- [ ] 恢复成功 / 失败有结构化记录，**失败实例进入重试队列重试一次**
- [ ] 每个成功恢复的实例，产出可审计的日志（xtrabackup 日志 + 查询验证日志）
- [ ] 最终 Markdown 报告 + 企业微信通知
- [ ] **底线：演练过程零生产事故**（演练在隔离的恢复服务器上，与生产隔离）

## 8. 风险（立项阶段识别）
| 风险 | 等级 | 缓解 |
|---|---|---|
| xtrabackup 版本与 MySQL 版本不匹配导致恢复失败 | 高 | 安装匹配的 xtrabackup 版本矩阵 |
| 演练误连生产库 | 高 | 网络隔离 + 配置中生产库只读账号 + 白名单 |
| 上百实例全量演练耗时过长 | 中 | 并发控制 + 断点续跑 |
| 多版本 MySQL 共存冲突 | 中 | 用 tarball 独立目录隔离，端口/data 路径分离 |
