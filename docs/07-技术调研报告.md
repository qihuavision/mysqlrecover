# 技术调研报告

> 本文档沉淀项目立项后的两轮 GitHub 开源项目调研结论。
> 调研目的：寻找可复用的开源实现，避免重复造轮子。
> 调研时间：2026-08-13
> 结论已锁定为 [ADR-08](99-交接文档.md#4-架构决策全部锁定可直接照此编码)，见第 4 节。

---

## 调研背景

本项目核心能力分两块：
1. **备份**：XtraBackup 自动化备份（全量/增量、压缩、本地+NAS 远程、保留策略）
2. **恢复演练**：多版本 MySQL 恢复 + 验证 + 审计报告

调研围绕这两块分别进行，评估标准见各章节。

---

## 第一轮：恢复演练方向（已确定借鉴 restore-drill）

### 调研维度

| 能力 | 说明 |
|---|---|
| 多版本 MySQL 共存 | 一台机器装多个版本实例（用户提的迂回方案） |
| 自动恢复演练 | 从备份 restore + 按版本路由到对应实例 |
| 恢复验证 + 报告 | 登录查询验证 + 出审计报告 |

### 候选项目评估

#### 1. restore-drill（`RamazanKara/restore-drill`）⭐ 已选定借鉴

- **语言**：Go | **License**：Apache 2.0 | 🔗 https://github.com/RamazanKara/restore-drill
- **定位**：通用备份恢复演练引擎，支持 PostgreSQL/MySQL/Redis/etcd
- **借鉴价值**：★★★★★

| 能力 | 覆盖 | 说明 |
|---|---|---|
| 多版本共存 | ✅ | **Docker 容器隔离**（每次恢复起对应版本镜像 `mysql:8.0`） |
| 自动恢复演练 | ✅ | 核心功能，声明式 YAML 配置 |
| 恢复验证 | ✅ | 验证 SQL + **HTML 审计报告** + RTO/RPO 证据 |

**选定理由**：
1. 用 Docker 隔离解决多版本问题 —— 比物理多实例（dbdeployer）更干净，每次恢复全新环境
2. 声明式 drill 配置（YAML）设计优秀，值得借鉴
3. HTML 审计报告 + RTO/RPO 证据正好满足"供领导审计"需求
4. **原生支持 xtrabackup**（backup tool 列表明确含 xtrabackup）

**不直接 fork 的原因**：Go 写的，与本项目 Python 3.11 技术栈不符。借鉴其设计思路，自己用 Python 实现。

#### 2. mneme（`WiseOpsTeam/mneme`）—— 备选参考

- **语言**：Python（Ansible）| **License**：MIT
- **定位**：MariaDB 灾备恢复 as Code
- **价值**：drill/verify 模块设计思路有参考价值，但基于 Ansible + mariabackup，集成成本高，不采用。

#### 3. dbdeployer（`datacharmer/dbdeployer` → `ProxySQL/dbdeployer`）—— 已评估未采用

- **定位**：单机多版本 MySQL 沙箱管理工具
- **评估结论**：虽然完美解决"多版本共存"，但本项目最终选择 **Docker 容器隔离** 方案（restore-drill 思路），比 dbdeployer 的物理多实例更干净、更易清理。dbdeployer 作为备选方案保留，若 Docker 方案受阻可回退。

#### 4. SCPR/restore-percona-backup —— 已评估未采用

- 增量恢复逻辑有参考价值，但功能单一、无验证、无多版本，不采用。

## 第二轮：备份方向（已确定以 pyxtrabackup 架构为师）

### 调研维度

| 能力 | 说明 |
|---|---|
| 自动化调度 | 定时备份 |
| 压缩 | 必须支持 |
| 本地备份 | 必须支持 |
| 远程 NAS 备份 | 推到 NAS |
| 全量 + 增量 | 行业标配 |
| 保留策略 | 自动清理旧备份 |

### 候选项目评估

#### 1. pyxtrabackup（`deviantony/xtrabackup-scripts`）⭐ 已选定架构借鉴

- **语言**：Python | **License**：Apache 2.0 | 🔗 https://github.com/deviantony/xtrabackup-scripts
- **定位**：Percona XtraBackup 的 Python wrapper，支持全量+增量
- **借鉴价值**：★★★★★（作为架构标杆）

**工程优点（决定借鉴的关键）**：
1. **命令执行用列表参数**，无 shell 注入风险（对比 pyxtra 的字符串拼接）
2. **完善的异常处理**：自定义 `ProcessError` + try/except/clean 模式 + 失败 exit 1
3. **正规 logging 日志框架** + 每步耗时计时
4. **模块化分层**：`command_executor` / `backup_tools` / `restoration_tools` / `filesystem_utils`
5. **增量备份用 LSN 追踪**（从 `xtrabackup_checkpoints` 读 `to_lsn`），比目录追踪健壮
6. **10 步备份流水线**：prerequisites check → workdir → backup → prepare → archive(compress) → transfer → clean → webhook
7. 有前置检查、失败自动清理、pip 可安装

**必须改造的点**：
| 问题 | 改造方案 |
|---|---|
| 🔴 用 `innobackupex`（XtraBackup 2.4 已废弃，8.0 移除） | 全部替换为 `xtrabackup` 命令 + 参数调整 |
| 🟡 项目已停止维护（作者公开找接手人） | 自己维护，不依赖上游 |
| 🟡 密码在命令行传递（`ps` 可见） | 改为 `--defaults-file` 或 stdin |
| 🟡 增量恢复靠文件名约定解析 | 改为元数据库记录 |
| 🟡 恢复前清空 datadir 无确认 | 加 `--yes` 确认 + 非空检测 |
| ❌ 无保留策略 | 新增（按天数/份数清理） |
| ❌ 无远程 NAS | 新增 rsync 推送 |
| ❌ 单实例 | 改为多实例配置驱动 |

**结论**：不直接 fork（依赖太老：Python 3.4/innobackupex/docopt），但**以其模块分层架构和工程实践为标杆**重写。

#### 2. pyxtra（`liron-li/pyxtra`）—— 已评估，仅参考 rsync 远程逻辑

- **语言**：Python | 🔗 https://github.com/liron-li/pyxtra
- **审计结论**：思路正确但工程不合格的原型脚本（shell 注入、密码硬编码 123456、增量链断裂、恢复无确认）。
- **唯一借鉴点**：`rsync -avrP` 远程推送备份的命令用法（用于 NAS 远程备份功能）。

#### 3. gox（`toorop/gox`）—— 已评估，借鉴设计思路

- **语言**：Go | 借鉴点：YAML 配置驱动、qpress 并行压缩、duration 保留策略字段。语言不符不集成。

#### 4. 其他（AliSQLBackup / database-backup / backup-scripts）—— 未采用

- AliSQLBackup：阿里内部 C++ 魔改，不适用
- database-backup：Shell，远程只支持 OSS 非 NAS
- backup-scripts：Shell 片段素材库

## 第三部分：两轮调研综合结论 —— 技术选型锁定

### 完整工具 = 三块拼图

```
┌──────────────────────────────────────────────────────┐
│        MySQL 自动备份 + 恢复演练工具                    │
├──────────────┬────────────────────┬──────────────────┤
│  ① 备份模块   │  ② 恢复演练模块     │  ③ 验证报告模块   │
│              │                    │                  │
│ 架构标杆:     │ 设计借鉴:          │ 设计借鉴:         │
│ pyxtrabackup │ restore-drill      │ restore-drill    │
│              │                    │                  │
│ - 全量/增量   │ - Docker 起对应    │ - 验证 SQL       │
│   (LSN追踪)  │   版本 MySQL 镜像  │ - HTML/MD 报告   │
│ - xtrabackup │ - xtrabackup 恢复  │ - RTO/RPO 证据   │
│   8.0 命令   │ - 按版本路由       │ - 企业微信通知    │
│ - 压缩打包   │                    │                  │
│ - 本地+NAS   │                    │                  │
│   (rsync)    │                    │                  │
│ - 保留策略   │                    │                  │
└──────────────┴────────────────────┴──────────────────┘
```

### 关键决策（对应 ADR-08）

| 决策点 | 选定方案 | 理由 |
|---|---|---|
| 备份模块架构 | 以 pyxtrabackup 分层架构为标杆重写 | 工程规范最高、Python、Apache 2.0 |
| 备份命令 | `xtrabackup`（非 innobackupex） | 兼容 MySQL 8.0 |
| 增量追踪方式 | LSN（从 xtrabackup_checkpoints 读取） | 比 pyxtra 的目录追踪健壮 |
| 多版本恢复方案 | **Docker 容器隔离** | 借鉴 restore-drill，比 dbdeployer 物理多实例更干净 |
| 恢复演练设计 | 声明式配置 + 验证 SQL + 审计报告 | 借鉴 restore-drill |
| 远程 NAS 备份 | rsync 推送 | 参考 pyxtra 的 rsync 用法 |
| 压缩 | tar.gz（备份模块内置） | 参考 pyxtrabackup |
| 保留策略 | 按天数/份数自动清理 | 新增（两个参考项目都没有） |
